## ① Загрузка изображений (`server/src/index.ts:2681–2845`, `supabase-store.ts`)

### M4. Нет валидации содержимого — принимается «картинка» любой природы
✅ **Исправлено** (`88fb71f`): `isPlausibleImage()` сверяет magic bytes с заявленным MIME (JPEG `FF D8 FF`, PNG, WEBP `RIFF…WEBP`); тесты: `<html>` как jpeg/png/webp → 400, валидный JPEG проходит, oversize по-прежнему 413.
`uploadImageData()` проверяет только **заявленный** MIME в data-URL (regex `image/(jpeg|png|webp)`) и размер в кодированных байтах (≤3 МБ). **Магические байты не проверяются.**

> 🧪 Подтверждено: `data:image/webp;base64,<html><script>alert(1)</script></html>` → `200 ok`, файл сохранён как «webp».

При конфигурированном Supabase мусорный бинарник с `.webp`/`.jpg`-расширением попадает в **публичный** бакет. Фронтенд рендерит только через `<img src>` (React, без `dangerouslySetInnerHTML`), поэтому прямой XSS сейчас закрыт — но защита держится на дисциплине фронтовика, а не на сервере.
**Фикс:** проверка сигнатур (JPEG/PNG/WEBP magic bytes) + по возможности декод-валидация; comment «decoded image limit» врёт — проверяются encoded-байты.

### M5. Галерея без ограничений → DoS всего каталога
✅ **Исправлено** (`88fb71f`): `validateGalleryItems()` — ≤12 элементов и ≤2000 символов у не-data-URL элементов в обоих маршрутах (create + update), 400 `gallery_too_large` / `gallery_item_too_long`. Покрыто тестами (13 → 400, 12 → 200, 2001-символьный элемент → 400).
Длина массива `body.gallery` и суммарный объём **не ограничены** (лишь общий `bodyLimit: 150 МБ`). Без Supabase data-URL хранится прямо в SQLite (`products.img` / `products.gallery`) и **отдаётся в каждом публичном** `GET /v1/products`.

> 🧪 Подтверждено: 10 × 3 МБ в одном товаре → `length(gallery) ≈ 40 МБ+` в строке БД и **40 МБ+ в каждом публичном ответе** `/v1/products` для каждого посетителя. Дополнительно разрастается файл БД, который каждые 30 с аплоадится в Supabase (трафик/стоимость).

**Фикс:** лимит на количество изображений (≤12) и суммарный объём на товар (≤20–30 МБ) в обоих маршрутах (`POST /v1/admin/products`, `POST .../:id/update`), код 413 при превышении.

### M6. `POST /v1/admin/products` — нулевая валидация полей
✅ **Исправлено** (`88fb71f`): `productCreateSchema` / `productUpdateSchema` (zod): `id` — только slug `^[a-zA-Z0-9][a-zA-Z0-9-]{0,59}$` (path-компоненты невозможны), `price`/`stock` — int в диапазонах, `name` ≤120, `volume` ≤40, `badge` ≤20, `cat` — enum; 400 `invalid_product` с деталями. Тесты: `../evil/../../x`, строковая цена, 121-символьное имя, `cat:"weapons"` — всё отклоняется.
`id`, `name`, `cat`, `price`, `stock` пишутся в БД **без zod-схемы и без обрезки** (в отличие от всех остальных admin-маршрутов). `id` может содержать `/`, `..`, произвольные символы.

> 🧪 Подтверждено: создан товар с `id: "../evil/../../x"`, `price: "abc"`, `name` 5000 символов — всё персистится. `price="abc"` попадёт в серверный расчёт цен (NaN-вектор), а `id` уходит в имя объекта Supabase `products/${pid}-...` — **path-компонент публичного бакета**.

**Фикс:** zod-схема (id: `^[a-z0-9-]{1,60}$`, price: int 0..1e8, name ≤120, cat: enum) + санитизация `pid` перед сборкой пути объекта.

### M7. Глобальный `bodyLimit: 150 МБ` на ВСЕ POST
✅ **Исправлено** (`88fb71f`): дефолтный лимит 2 МБ на все маршруты; media-маршруты получают явные исключения (image/gallery-image 5 МБ, products create/update 60 МБ, content 5.5 МБ, stories 15 МБ) через `preParsing`-хук по Content-Length. Примечание: per-route `config.bodyLimit` в Fastify v5 **не работает** (проверено на v5.11.3) — хук и есть реализация. Тесты: 3 МБ на `/v1/orders` → 413, JPEG 2.2 МБ на image-маршрут → 200.
150 МБ нужны только 4 image-маршрутам, но сейчас любой клиент может прислать 150 МБ JSON на любой эндпоинт (парсинг в память → DoS на CPU/память).
**Фикс:** глобально ~1–2 МБ + `config: { bodyLimit: 150 МБ }` только на `.../image`, `.../gallery-image`, `POST /v1/admin/products`, `.../:id/update`.

### Низкие
- **L3.** Имя объекта `products/${pid}-${Date.now()}` — коллизия в одной миллисекунде → тихий перезапис; `Math.random` не используется, но для security-токенов см. L3b: коды QR/сертификатов/B2B генерируются `Math.random` (`genHumanCode`) — предсказуемость PRNG не даёт attacker-у преимущества (коды независимы), но `crypto.randomBytes` здесь бесплатно и правильно.
- Positive: маршруты только под `ensureAdmin`; allowlist MIME; CORS без `*`; на ответах `X-Content-Type-Options: nosniff`.

## ② B2B rate limiting (`index.ts:3395`, `:1509`, `:257`)

### H3. `/v1/b2b/verify` — оракль для brute-force без rate-limit, lockout и требований к энтропии
✅ **Исправлено** (`5eb3fa0`): per-route `rateLimit: { max: 5, timeWindow: "1 minute" }` (ключ — подписанный субъект после H2); `warn`-лог каждой неудачной верификации (ip, tgId, код) и invalid-b2b в `/v1/orders`; при создании кода ≥8 символов `A-Z0-9`, иначе 400 `code_too_weak`; авто-код теперь `B2B-XXXXXXXX` (32⁸≈1.1e12). 6+1 тест.
Три усугубляющих фактора работают вместе:

1. **Нет per-route лимита** — действует только глобальный 300 req/мин **per IP**. Второй оракль — `POST /v1/orders` (`invalid_b2b_code`, 15/мин per session).
2. **Аутентификация тривиальна:** достаточно анонимной browser-session (отрицательный `tg_id`, TTL **30 дней**, выпуск 1 req) — реальный Telegram не нужен.
3. **Коды без требования энтропии:** `POST /v1/admin/b2b-codes` принимает строку длиной **4–40** (`B2B-AB`, `OZOD2026` — что угодно). Дефолт `B2B-XXXXXX` (32⁶ ≈ 1 млрд) терпим, но короткие коды тривиальны.

> 🧪 Подтверждено:
> - анонимная session проходит `401`-гейт `verify`;
> - 350 попыток с одной IP дают 429 только при исчерпании **глобального** бюджета (~300), per-route лимита нет;
> - код `B2B-AB` (percent 70) найден вслепую за **3 проб** последовательным перебором — без lockout и без логов неудач.

**Влияние:** партнёрская скидка до **70%** на оптовые заказы у посторонних.
**Фикс (комбинация):**
- `rateLimit: { max: 5, timeWindow: "1 minute", keyGenerator: (tgId + ip) }` на `verify` (и адекватный лимит на `orders` уже есть);
- при создании кода: минимум 8 символов из `A-Z0-9` (32⁸ ≈ 1.1e12) — либо запрет произвольных «читаемых» кодов;
- логирование/алерт на серии неудачных верификаций (сейчас атаки бесследны);
- опционально: unified-ответ `invalid` на «не найден/не активен» (текущий 404 с `not_found` — нормальный oracle, это и есть целевое поведение защиты, просто нужны лимиты).

### H2. `trustProxy: true` + нечищенный X-Forwarded-For → **обход ВСЕХ IP-лимитов**
✅ **Исправлено** (`b2ab7c0`): (a) worker перепишет `X-Forwarded-For` на `CF-Connecting-IP` до прокси-запроса (поддельный префикс отбрасывается — проверено стимулом); (b) ключ лимитера переведён на подписанного субъекта, поэтому `req.ip` больше не является основным вектором обхода для money-маршрутов; residual: при прямом обращении к Fastify без edge-санитизации IP-bucket'и всё ещё spoof-ятся — задокументирован как инвариант в `index.ts` (связка с Render/CF обязана прогонять через worker). (c) allowlist-функция `trustProxy` оставлена на будущее (см. бэклог). 3 теста (`rate-limit.test.ts`).
`index.ts:227` доверяет XFF от любого апстрима, а Cloudflare-worker (`worker.js`) пересылает клиентские заголовки как есть (Cloudflare дописывает реальный IP **в конец** списка — левее оказывается значение атакующего). Fastify берёт левый адрес → `req.ip` под контролем клиента.

> 🧪 Подтверждено: 12 запросов с одинаковым `X-Forwarded-For` → 2 шт. 429 (лимит работает); 12 запросов с **12 разными поддельными XFF** → 12×200, ни одного 429.

Поражено всё IP-keyed: глобальные 300/мин, `browser-session` 10/мин, `returns` 10/час, `chat` 10/мин, `broadcast` 2/мин. Единственный надёжный лимит — `POST /v1/orders` (keyGenerator по signed-заголовку).
**Фикс:** (a) в worker — перезапись `X-Forwarded-For: <real client ip>` (без наследования входящего); (b) в Fastify — `trustProxy` как массив/функция с allowlist'ом IP прокси (Render/CF egress) вместо `true`; (c) для критичных маршрутов — keyGenerator по аутентифицированному субъекту, как в `orders`.

### M1. Тот же класс орակлей: промокоды и сертификаты
✅ **Исправлено** (`5eb3fa0`): `promo/validate` (публичный) и `certificates/check` — 10/мин на субъекта/IP. Энтропия промо/сертификат-кодов не повышена осознанно: это короткие маркетинговые коды (`DELIS15`), а лимит + субъектный ключ + зачищенный edge дают ≤100 попыток/мин/IP (10 session × 10). Тесты: 11-я попытка → 429 в обоих маршрутах.
- `GET /v1/promo/validate` — **публичный, без аутентификации**, 300/мин per IP; промокоды создаются admin'ом без нижней границы энтропии (2–40 символов, `A-Z0-9_-`). Короткий промокод (до 90% скидки) перебираем.
- `POST /v1/certificates/check` — сериализованный oracle статусов сертификата (до 5 000 000 сум); коды `GIFT-XXXXXX` (32⁶) с одним IP — ~19 дней, с пулом IP — дни/часы.
**Фикс:** те же меры: per-route лимиты (публичный `promo/validate` — 10/мин per IP + per session), энтропия кодов (≥8), алерты.

## ③ Telegram-кнопки статусов (`server/src/bot.ts`)

### H1. `/track` — IDOR: любой пользователь бота видит чужие заказы
✅ **Исправлено** (`24bdd65`): вынесен `trackOrderLookup()` — пользователь ищет только заказы с `tg_id = его id` (и по id, и по BTS в `courier_note`); admin (user-id) и допущенные курьерские chat'ы — любые; без identity — ничего. 8 unit-тестов, включая перебор чужого id и чужого BTS-кода.
`bot.command("track")` ищет заказ по ID **или** по подстроке в `courier_note` (свободный текст admin'а) и отвечает статус, сумму, дату и зону доставки — **без какой-либо проверки владельца** (`ctx.from.id` не сравнивается ни с `order.tg_id`, ни с `ADMIN_CHAT_ID`, ни с `COURIER_IDS`).

Номера заказов — `DL-1000…DL-9999` (9 000 значений) → полный перебор за минуты даже с учётом flood-лимита Telegram. Это утечка данных о заказах (кто что заказал, сколько платит, в какой регион) всем пользователям бота.
**Фикс:** допустимы только `ctx.from.id === order.tg_id || ADMIN_CHAT_ID || COURIER_IDS.has(chat)`; поиск по `courier_note` — вообще убрать из публичной команды (или оставить владельцу; BTS-коды выдавать клиенту отдельно и проверять точным совпадением).

### M2. Legacy-каббэк `order_accept_*` — смена статуса заказа БЕЗ проверки admin
✅ **Исправлено** (`2bfb988`): добавлен тот же admin-гейт, что и у `order_status_*` (`ctx.from?.id !== ADMIN_CHAT_ID` → «⛔ Faqat admin / Только для админа»). Удаление legacy-кнопки из уведомлений — в бэклог.
```ts
bot.callbackQuery(/^order_accept_(.+)$/, async (ctx) => {
  const orderId = ctx.match![1];
  const result = await transitionOrderStatus(db, orderId, "preparing"); // ← кто угодно
```
В отличие от нового `order_status_*` (где есть `ctx.from?.id === ADMIN_CHAT_ID`), legacy-обработчик **не проверяет ни одного условия**. Кнопка висит в уведомлении admin'а, но Telegram **сохраняет inline-кнопки при пересылке**: admin переслал уведомление коллеге/в группу — любой читатель может двинуть заказ в `preparing` (status-переход сам по себе безвреден для денег/остатков, но это дыра в модели авторизации + способ «зависнуть» заказ в нужном состоянии).
**Фикс:** добавить тот же admin-check; в идеале убрать legacy-кнопку из уведомлений (осталась только в fallback-пути `web_app_data`).

### M3. Непоследовательная модель «кто admin» в боте (user-id vs chat-id)
✅ **Исправлено частично** (`2bfb988`): в **личном** чате админа (положительный ID) ответ support сохраняется и уходит клиенту только от самого админа-пользователя — имперсонация членом группы/соседом закрыта. **Residual (осознанный):** при отрицательном (групповом) `ADMIN_CHAT_ID` сохраняется chat-scoped поведение — полноценное решение требует явного allowlist'а staff-user-id'ов, оставлено в бэклоге; readiness-предупреждение о групповом ID — в бэклог (M8-коммит покрывает только dev-токен).
- `order_status_*`, `/broadcast` — проверяют **`ctx.from.id === ADMIN_CHAT_ID`** (строго).
- Ответы на support — проверяют **`ctx.chat.id === ADMIN_CHAT_ID`**: если `ADMIN_CHAT_ID` — **групповой** чат, любой участник группы, ответивший на сообщение поддержки, становится «менеджером»: текст сохраняется как ответ менеджера **и уходит клиенту** (имперсонация).
**Фикс:** единое правило: все admin-операции — `ctx.from.id === ADMIN_CHAT_ID`; документировать, что `ADMIN_CHAT_ID` должен быть личным чатом (в readiness-check добавить предупреждение при отрицательном ID).

### Низкие
- **L1.** ✅ **Исправлено** (`2bfb988`): `decideStarsPayment()` — заказ помечается paid только если payer = `order.tg_id` или admin; forwarded payment / чужой payload → skip + `warn`/`error`-лог + уведомление админа «оплата НЕ применена»; 5 unit-тестов.

- Positive: `esc()` на всю пользовательскую HTML-вкладку в сообщениях; `pre_checkout_query` валидирует payload по БД; ownership на `/v1/me/*`, `orders/:id`, `track` (API-часть), `returns`, `subscriptions` (`sub_cancel_` — owner-scoped ✓).
